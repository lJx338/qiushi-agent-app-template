01 / 先确认现在能做什么

本仓库只有应用、开发依赖和说明，没有平台主项目。SDK、模拟执行器、检查、预览和打包来自固定版本 @qiushi/app-kit。

这是开发工具，不是已上线的 SaaS。
可做业务逻辑、schema、合成测试及平台 UI extension；真实登录、租户权限、飞书/腾讯、持久审批和应用安装后台仍待平台实现。不要把模拟成功写成生产验收。
创建应用PRD + AI 开发预览与验证打包交付后续：后台授权启用

02 / 环境准备与第一次运行

先拉取你有权限访问的私有模板仓库，并进入目录。使用 .nvmrc 指定的 Node 22.23.2；已安装 nvm 时执行：

nvm install
nvm use
npm ci
npm run verify
npm run app:run
npm run app:dev

当前验收环境是 macOS/Linux；Windows 可使用 WSL2，原生 Windows 尚未验收。没有 nvm 时，用其他版本管理器安装同一 Node 版本。分发的模板含 lock；全新生成目录若尚无 lock，先执行一次 npm install。后续团队和 CI 一律用 npm ci。

app:dev 会输出 http://127.0.0.1:随机端口。用浏览器打开，Ctrl+C 结束；不要使用教程中猜测的固定端口。默认样板会为“甲企业测试客户”创建模拟草稿。

03 / 创建属于你的应用

样板仓库用于快速验收。把下方的应用名和负责人改成实际任务内容，生成到一个不存在的新目录：

npm run app:create -- crm-assistant --name "客户管理 Agent" --owner YOUR_GITHUB_LOGIN --out ../crm-assistant
cd ../crm-assistant
npm install
npm run verify

生成器会带上 SDK 依赖归档、规范、HTML 教程、测试和 CI。随后只打开 crm-assistant 这个新目录给 AI，并为它建立自己的私有 Git 仓库。无需克隆平台源码，也不需要把业务源码发回平台仓库。

生成器拒绝覆盖已有目录。每个应用使用自己的 slug、appId、工具名和 owner；应用名称可以是中文，slug 使用小写字母、数字与连字符。

04 / 给 AI 一份能执行的任务

先补全 docs/PRD.md，至少写清用户、业务范围、输入输出、权限、验收样例和缺失平台能力。不要只说“做一个 CRM”。下面的指令可以复制后修改：

阅读根 AGENTS.md、docs/DEVELOPMENT.md、docs/PRD.md、
docs/PERMISSIONS.md 和 docs/FRONTEND.md。
这是独立业务应用仓库，不是平台主项目。
先复述任务范围、分支和允许修改路径。
业务只修改 src、schemas、fixtures、tests、presets 及本应用 docs。
不修改 vendor、node_modules、工具链、CI 或依赖版本来绕过检查。
只使用 @qiushi/app-kit 已提供的契约。
缺平台能力时列出接口需求和阻塞，不克隆平台仓库自行修改。
完成正常、无权限、错误输入和重复提交测试。
执行 npm run verify 和 npm run app:pack。
交付真实结果、变更文件清单和仍未实现的能力，不自行部署生产。

一个任务一个短分支，一个 AI 会话一个独立工作目录。AGENTS 能指导 AI，但不是文件写保护；开发者仍需核对变更清单和业务结果。

05 / 应用代码放在哪里

文件 / 目录你的工作
src/app.ts定义业务动作；通过 execution.data 使用有边界的数据能力。
src/host.ts通过 kit/dsh 注册 DSH 工具；没有真实 qsBusiness 必须拒绝。
src/client/index.tsx声明 qiushi.ui.v1 的 form/table/conversation/mixed 页面；只使用宿主 bridge，不读 cookie、DSH session/端口或凭证。
schemas / app.manifest.json输入、输出、配置、动作、UI、数据依赖、权限、副作用和版本保持一致。
fixtures / tests合成数据、正常路径、拒绝路径和独立业务算例。
docs岗位 PRD、权限规格、前端规则、开发教程和验收证据。
vendor / package-lock.json平台提供的固定开发依赖与完整性记录，不直接编辑归档。

金额和业务状态用确定性逻辑。模型输入、外部文档及工具输出是数据，不能授予权限。共享飞书应用身份与员工身份不同；不能用机器人绕过员工无权。

界面延续白底蓝色，主色 #1d63ff。布局、状态与窄屏要求见 前端规范；共享样式 token 由开发包提供。

06 / 预览、测试与定位错误

npm run app:check
npm run app:test
npm run typecheck
npm run app:dev
# 完整本地门禁
npm run verify

开发预览提供合成租户、无权限和停用场景。修改业务输入后使用新的幂等键；同一意图重复点击应去重，不同参数复用同键应冲突。数据在内存中，重启即清空。

预览是 JSON 动作表单。它可以验证契约和业务执行，但不能证明正式 UI、真实客户数据、生产隔离或长任务恢复已经完成。

运行失败时给 AI 提供：命令、退出结果、Node/npm 版本、当前 commit、最小合成输入。不要提供真实凭证，也不要要求它删掉失败测试。

07 / 在应用仓库提交，再交付制品

创建任务分支，例如 feat/customer-search。提交前查看 git status --short 和 git diff，检查是否混入依赖篡改、密钥或无关文件。

npm run verify
npm run app:pack

打包输出到 .local/artifacts/：一个应用 tgz 和一个 release.json，包含版本、SHA-256、manifest 与未完成门槛。不提交 .local、dist 或 node_modules。vendor 中的平台开发包是明确允许提交的版本化依赖，性质不同。

源码在本应用仓库提 PR；本仓库 CI 会运行安装、验证和打包。应用发布后，目标流程是“平台后台登记制品 → 校验兼容性 → 上架 → 企业选择数据、授权并启用”。后台目前未实现，开发包不能直接生产启用。需要客户端装配的 DSH 插件，后续由平台流水线处理。

不要直接推 main。仓库评审人、成员权限与主干保护须实际配置；CI 成功不等于已获得独立业务批准。

08 / 常见问题

AI 说需要修改平台，怎么办？

把缺少的能力、输入输出、权限和验收样例写进本应用 PRD，交给平台负责人。应用继续开发不依赖该接口的部分，不自行克隆平台或复制 SDK。

找不到开发包 / npm ci 失败？

确认 vendor 内归档存在、使用正确 Node、package 与 lock 一致。新生成目录先 npm install；已经带 lock 的团队仓库若不一致，定位变更原因，不能随意删除 lock 或使用最新版依赖。

能否直接拿自己的 React 页面作为插件？

只能通过 @qiushi/app-kit/ui 和平台宿主 bridge 声明页面。React/ReactDOM 只作为 peer，由平台单一宿主提供；不得打包副本、直连平台/DSH、读取 cookie 或凭证。

为什么 --release 失败？

这是预期门禁：真实登录、provider、DSH 集成和可信发布证据尚未完成。不要修改 stage 或 productionReady 使它通过。

09 / 交付前最后核对

  • 应用 PRD 与权限规格完整，业务样例有独立预期值。
  • manifest、schema、实现和测试一致，没有客户数据或凭证。
  • verify 通过，开发包及摘要可定位，未提交业务构建产物。
  • 代码只改变本任务范围；列出所有共享能力缺口。
  • 说明哪些是模拟、哪些是真实集成、哪些仍未实现。
  • 在本应用仓库提交 PR，交付制品，不合并源码到平台。

平台边界与设计顺序

你的应用用于客户前台，公司内部运营后台独立登录。应用不开发登录、租户切换、后台管理或跨端单点登录。

先完善 PRD、页面、权限与数据字段，再使用当前版本 SDK 实现。缺少数据库、文件或持久任务能力时记录平台契约需求，不能编造接口、修改 vendor 或克隆平台源码补齐。

模板规范源与公开模板同步维护；已分发 kit 内置生成器的规范要等新版本发布才更新，仓库文档更新不等于 SDK 已升级。
